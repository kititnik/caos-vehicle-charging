## 1. Условие задачи

На зарядной станции установлены устройства нескольких типов. Электромобили прибывают с различным уровнем заряда, ёмкостью аккумулятора и поддерживаемыми разъёмами. Автомобиль запрашивает совместимое устройство и требуемый конечный уровень заряда. Если подходящее устройство занято, автомобиль ожидает в очереди либо покидает станцию после тайм-аута. Станция имеет общий предел мощности, который диспетчер распределяет между активными зарядками (равномерно, приоритетно или адаптивно) тактами.

**Входные параметры:** 
- число, типы и мощность устройств; 
- предел мощности станции; 
- количество и характеристики автомобилей; 
- начальный и требуемый уровень заряда; 
- интервалы прибытия; 
- максимальное время ожидания; 
- стратегия выбора устройства и распределения мощности; 
- продолжительность такта.

**Инварианты:** 
- одно устройство обслуживает не более одного автомобиля; 
- подключение только к совместимому устройству; 
- суммарная мощность не превышает предел станции; 
- заряд не превышает ёмкость; 
- зарядившийся автомобиль освобождает устройство.

**Завершение:** после зарядки или ухода всех автомобилей, по окончании периода работы, либо по прерыванию пользователем.

## 2. Сценарий модели

Моделирование идёт тактами. Каждый участник модели - самостоятельный объект и отдельный процесс, подписанный на событие такта. Внутри такта процессы работают группами в фиксированном порядке (`TickOrder`), процессы одной группы - параллельно:

1. **Автомобиль** (`vehicle_on_tick`, процесс на каждую машину) - в свой такт прибытия запрашивает устройство у станции: если совместимых разъёмов на станции нет, уезжает, иначе встаёт в очередь. Если время ожидания истекло, а устройство так и не назначено, покидает очередь.
2. **Станция** (`station_on_tick`, один процесс) - проходит очередь по порядку и подключает машины к свободным совместимым устройствам по стратегии выбора, затем распределяет мощность между занятыми устройствами.
3. **Зарядное устройство** (`charger_on_tick`, процесс на каждое устройство) - передаёт в машину энергию `мощность × длительность такта`; при достижении целевого заряда отключает машину и освобождается.

Главный процесс управляет временем: в `sim_tick` для каждой группы он выдаёт каждому её процессу сигнал на запуск (`sem_post` на личный семафор процесса), затем ждёт столько сигналов `phase_done` (семафор группы), сколько в ней процессов, и только после этого запускает следующую группу. Личный семафор у каждого процесса нужен, чтобы быстрый процесс не мог забрать чужой сигнал и отработать такт дважды. После трёх групп номер такта увеличивается.

Состояния автомобиля (`CarState`): `PENDING → QUEUED → CHARGING → DONE`, либо `QUEUED → TIMED_OUT`, либо `PENDING → INCOMPATIBLE`.

**Совместимость:** разъёмы хранятся битовыми масками (`TYPE1`, `TYPE2`, `CCS_COMBO`, `CHADEMO`, `TESLA_NACS`), у машины их может быть несколько.

**Стратегии выбора устройства:** `first_fit` - первое подходящее, `max_power` / `min_power` - с наибольшей / наименьшей мощностью.

**Стратегии распределения мощности:**
- `uniform` - поровну;
- `adaptive` - пропорционально недостающей до цели энергии;
- `priority` - машина, прибывшая раньше, берёт сколько может, остаток переходит следующей.

**Обеспечение инвариантов:**

| Инвариант | Где обеспечивается |
|---|---|
| одно устройство - одна машина | `charger_attach` отказывает занятому устройству |
| только совместимое устройство | `charger_attach`, `find_free_charger` проверяют маску разъёмов |
| сумма <= предела станции | распределение раздаёт не больше `power_limit` |
| заряд <= ёмкости | `vehicle_charge` обрезает заряд по цели |
| зарядившаяся машина освобождает устройство | `charger_on_tick` вызывает `charger_detach` |

**Реализации.** Логика модели общая, различается запуск процессов и способ обмена данными:

| № | Исполняемые файлы | Запуск процессов | Обмен данными | Семафоры POSIX |
|---|---|---|---|---|
| 1 | `caos_named` | `fork` | разделяемая память | именованные |
| 2 | `caos_unnamed` | `fork` | разделяемая память | неименованные |
| 3 | `cvc_coordinator`, `cvc_participant` | независимо | разделяемая память | именованные |
| 4 | `cvc_fifo_coordinator`, `cvc_fifo_participant` | независимо | именованные каналы (FIFO) | именованные |

Программа 3. Координатор читает конфигурацию, создаёт разделяемую память и семафоры, затем ждёт участников. Участник получает роль и номер (`--role`, `--index`), подключается к объектам запуска `--run` и сообщает о себе через семафор `ready`. Если координатор ещё не запущен, участник повторяет попытку раз в 100 мс. Порядок запуска не важен.

Программа 4. Разделяемой памяти нет: состояние модели (`World`) хранится в обычной памяти координатора. У каждого участника два канала: `/tmp/cvc_<run>_<роль>_<номер>_down` и `..._up`. Перед своей группой участник получает всё состояние по `down`, выполняет свой обработчик и возвращает состояние по `up`. Координатор применяет из ответа только то, что мог изменить этот участник (`apply`). Участники одной группы работают с копиями, поэтому очередь станции координатор меняет сам, по смене состояния машины. Семафоры задают только порядок действий и защищают вывод в журнал, данные по ним не передаются.

## 3. Пользовательский интерфейс

Программа консольная, параметры задаются конфигурационным файлом:

```bash
./build/caos_named --config station.cfg
./build/caos_unnamed --config station.cfg
./run_independent.sh --config station.cfg
./run_fifo.sh --config station.cfg
```

Скрипты запускают все процессы из одного терминала. Процессы программ 3 и 4 можно запускать вручную, в разных терминалах, в любом порядке:

```bash
./build/cvc_coordinator --config station.cfg [--run <id>]
./build/cvc_participant --role vehicle|station|charger [--index n] [--run <id>]
```

Для программы 4 используются `cvc_fifo_coordinator` и `cvc_fifo_participant` с теми же аргументами.

Формат конфигурации (`#` — комментарий):

```
power_limit 50          # предел мощности станции, кВт
max_wait 3              # максимальное ожидание в очереди, тактов
distribution uniform    # uniform | priority | adaptive
selection first_fit     # first_fit | max_power | min_power
tick 0.25               # длительность такта, ч
display_delay 500       # задержка отображения такта, мс
mode limited 40         # limited <тактов> | unlimited
log log.txt             # файл журнала (необязательно)

# charger <разъём> <мощность, кВт>
charger CCS_COMBO 50
# car <разъёмы через запятую> <ёмкость, кВт·ч> <старт, %> <цель, %> <мощность, кВт> <такт прибытия>
car CCS_COMBO,TYPE2 60 20 80 50 0
```

Обязательны хотя бы одно устройство и одна машина, `power_limit`, `tick` и `mode`.

Каждое событие выводится строкой с меткой такта `[t=N]` одновременно в stdout и в файл журнала. Вывод выполняется через файловые дескрипторы под семафором. Порядок строк в разных тактах и группах фиксирован, внутри одной группы строки разных процессов могут идти в любом порядке. Между тактами выдерживается задержка `display_delay` (`usleep`). В конце печатается итоговая статистика: причина завершения, число тактов и часов, количество машин по итоговому состоянию и заряд каждой машины.

## 4. Запуск и завершение

Сборка (проверено в Docker Ubuntu, `--platform linux/amd64`):

```bash
cmake -S . -B build && cmake --build build
```

| Ситуация | Поведение | Код возврата |
|---|---|---|
| все машины зарядились, ушли или несовместимы | «завершение: все машины обслужены» + статистика | 0 |
| `mode limited N` и прошло N тактов | «завершение: окончание периода» + статистика | 0 |
| Ctrl+C (SIGINT), в любом режиме | «моделирование прервано пользователем» + статистика | 130 |
| неверные аргументы | `Usage: ... --config <file>` | 1 |
| ошибка конфигурации | `<файл>:<строка>: syntax error / invalid value / missing required parameters` | 1 |

Обработчик SIGINT только поднимает флаг, главный цикл проверяет его между тактами, когда все процессы ожидают на семафорах. Затем `sim_stop` выставляет флаг остановки, будит все процессы и ждёт завершения дочерних (`waitpid`); только после этого удаляются семафоры и разделяемая память.

В программе 3 участник по SIGINT ставит флаг `stop` в разделяемой памяти, в программе 4 передаёт его координатору в ответе. Координатор программы 4 по завершении закрывает каналы, участники получают конец файла и выходят. Объекты удаляет только их создатель (координатор), участники лишь закрывают свои дескрипторы.
