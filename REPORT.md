**Вариант:** 33 - станция зарядки электромобилей

## 1. Условие задачи

На зарядной станции установлены устройства нескольких типов. Электромобили прибывают с различным уровнем заряда, ёмкостью аккумулятора и поддерживаемыми разъёмами. Автомобиль запрашивает совместимое устройство и требуемый конечный уровень заряда. Если подходящее устройство занято, автомобиль ожидает в очереди либо покидает станцию после тайм-аута. Станция имеет общий предел мощности, который диспетчер распределяет между активными зарядками (равномерно, приоритетно или адаптивно) тактами.

**Входные параметры:** 
- число, типы и мощность устройств; 
- предел мощности станции; 
- количество и характеристики автомобилей; 
- начальный и требуемый уровень заряда; 
- интервалы прибытия; 
- максимальное время ожидания; 
- стратегия выбора устройства и распределения мощности; 
- продолжительность такта.

**Инварианты:** 
- одно устройство обслуживает не более одного автомобиля; 
- подключение только к совместимому устройству; 
- суммарная мощность не превышает предел станции; 
- заряд не превышает ёмкость; 
- зарядившийся автомобиль освобождает устройство.

**Завершение:** после зарядки или ухода всех автомобилей, по окончании периода работы, либо по прерыванию пользователем.

## 2. Сценарий модели

Моделирование идёт тактами. Каждый участник модели - самостоятельный объект, подписанный на событие такта. Станция работает на сервере, каждая машина и каждое устройство - отдельный клиент (процесс), подключённый к серверу по TCP. Внутри такта участники обрабатываются по очереди в фиксированном порядке (`TickOrder`):

1. **Автомобиль** (`vehicle_decide`, клиент на каждую машину) - в свой такт прибытия запрашивает устройство у станции: если совместимых разъёмов на станции нет, уезжает, иначе встаёт в очередь. Если время ожидания истекло, а устройство так и не назначено, покидает очередь.
2. **Станция** (`station_on_tick`, сервер) - проходит очередь по порядку и подключает машины к свободным совместимым устройствам по стратегии выбора, затем распределяет мощность между занятыми устройствами.
3. **Зарядное устройство** (`vehicle_charge`, клиент на каждое устройство) - передаёт в машину энергию `мощность × длительность такта`; при достижении целевого заряда отключает машину и освобождается.

Сервер управляет временем: в `sim_tick` он отправляет каждому клиенту сообщение `MSG_TICK` с его текущим состоянием и ждёт ответа. Машина отвечает решением (`MSG_ACTION`: прибыть, уйти из очереди или ничего), устройство - новым зарядом машины (`MSG_RESULT`). Сервер применяет ответ сам и проверяет его. Пока ответа нет, следующий участник не обрабатывается, поэтому порядок групп сохраняется. Все сообщения - одна структура `Message`. Она передаётся целиком через `write`/`read`.

Состояния автомобиля (`CarState`): `PENDING → QUEUED → CHARGING → DONE`, либо `QUEUED → TIMED_OUT`, либо `PENDING → INCOMPATIBLE`.

**Совместимость:** разъёмы хранятся битовыми масками (`TYPE1`, `TYPE2`, `CCS_COMBO`, `CHADEMO`, `TESLA_NACS`), у машины их может быть несколько.

**Стратегии выбора устройства:** `first_fit` - первое подходящее, `max_power` / `min_power` - с наибольшей / наименьшей мощностью.

**Стратегии распределения мощности:**
- `uniform` - поровну;
- `adaptive` - пропорционально недостающей до цели энергии;
- `priority` - машина, прибывшая раньше, берёт сколько может, остаток переходит следующей.

**Обеспечение инвариантов:**

| Инвариант | Где обеспечивается |
|---|---|
| одно устройство - одна машина | `charger_attach` отказывает занятому устройству |
| только совместимое устройство | `charger_attach`, `find_free_charger` проверяют маску разъёмов |
| сумма <= предела станции | распределение раздаёт не больше `power_limit` |
| заряд <= ёмкости | `vehicle_charge` обрезает заряд по цели |
| зарядившаяся машина освобождает устройство | `charger_complete_tick` вызывает `charger_detach` |

**Программы:**

| Исполняемый файл | Роль |
|---|---|
| `cvc_server` | станция: очередь, назначение устройств, распределение мощности, журнал |
| `cvc_client` | машина или устройство, процесс на каждого участника |
| `cvc_observer` | наблюдатель (журнал всей модели) |
| `caos_vehicle_charging` | однопроцессная версия из задания 1 |

Сервер ждёт подключения всех участников (`accept`). Клиент при подключении сообщает роль и номер (`MSG_HELLO`), сервер отвечает начальным состоянием (`MSG_WELCOME`) или закрывает соединение, если номер неверный или уже занят. Между тактами сервер проверяет слушающий сокет через `select`.

**Наблюдатели.** Наблюдатель при подключении отправляет `MSG_WATCH`. Сервер добавляет его сокет в журнал (`Logger.watcher_fds`), и каждая строка журнала уходит наблюдателю обычным текстом. Наблюдателей может быть до 16 (`MAX_WATCHERS`), подключать и отключать их можно в любой момент.

**Отключение участников.** Если связь с машиной или устройством потеряна, сервер закрывает сокет и продолжает работу, а участник бездействует: машина не приезжает и не уходит из очереди, устройству (`Charger.offline`) не назначаются машины и не выделяется мощность. Клиент, запущенный заново с тем же номером, занимает свой слот и получает текущее состояние. Машина, пропустившая такт прибытия, приезжает в первый такт после возвращения.

## 3. Пользовательский интерфейс

Программа консольная, параметры задаются конфигурационным файлом:

```bash
./build/caos_vehicle_charging --config station.cfg
./run_tcp.sh --config station.cfg [port]
```

Скрипт запускает сервер и всех клиентов на 127.0.0.1 из одного терминала. Программы можно запускать вручную, адрес и порт задаются в командной строке:

```bash
./build/cvc_server --config station.cfg --address <ip> --port <port>
./build/cvc_client --address <ip> --port <port> --role vehicle|charger --index n
./build/cvc_observer --address <ip> --port <port>
```

Формат конфигурации (`#` - комментарий):

```
power_limit 50          # предел мощности станции, кВт
max_wait 3              # максимальное ожидание в очереди, тактов
distribution uniform    # uniform | priority | adaptive
selection first_fit     # first_fit | max_power | min_power
tick 0.25               # длительность такта, ч
display_delay 500       # задержка отображения такта, мс
mode limited 40         # limited <тактов> | unlimited
log log.txt             # файл журнала (необязательно)

# charger <разъём> <мощность, кВт>
charger CCS_COMBO 50
# car <разъёмы через запятую> <ёмкость, кВт·ч> <старт, %> <цель, %> <мощность, кВт> <такт прибытия>
car CCS_COMBO,TYPE2 60 20 80 50 0
```

Обязательны хотя бы одно устройство и одна машина, `power_limit`, `tick` и `mode`.

Сервер выводит каждое событие модели строкой с меткой такта `[t=N]` одновременно в stdout, в файл журнала и всем наблюдателям. Клиенты выводят только то, что получают при обмене.

## 4. Запуск и завершение

Сборка (проверено в Docker Ubuntu, `--platform linux/amd64`):

```bash
cmake -S . -B build && cmake --build build
```

| Ситуация | Поведение | Код возврата |
|---|---|---|
| все машины зарядились, ушли или несовместимы | «завершение: все машины обслужены» + статистика | 0 |
| `mode limited N` и прошло N тактов | «завершение: окончание периода» + статистика | 0 |
| Ctrl+C (SIGINT) или `kill` (SIGTERM), в любом режиме | «моделирование прервано пользователем» + статистика | 130 / 143 |
| неверный адрес или занятый порт | `cannot listen on <адрес>:<порт>` | 1 |
| ошибка конфигурации | `<файл>:<строка>: syntax error / invalid value / missing required parameters` | 1 |

Обработчик SIGINT и SIGTERM на сервере только поднимает флаг. После итогов сервер рассылает всем участникам `MSG_END` с итоговым состоянием и закрывает все сокеты. Клиенты по `MSG_END` пишут «моделирование завершено» и выходят с кодом 0, наблюдатели по концу соединения пишут «соединение с сервером закрыто». Если сервер завершился аварийно, клиенты пишут «связь с сервером потеряна» и выходят с кодом 1.

## 6. Дополнительные требования

| Требование | Реализация |
|---|---|
| комментарии в коде | есть во всех модулях |
| ввод-вывод через файловые дескрипторы | `logger.c`: `open` / `write` / `close`, `net.c`: `read` / `write` по сокетам |
| завершение по окончании работы и по прерыванию | обработка SIGINT и SIGTERM, `MSG_END` всем клиентам |
| сохранение лога со статистикой | ключ `log`, итоги в конце журнала (`stats.c`) |
| тестовые наборы и скрипт запуска | `tests/configs/*.cfg` (10 наборов), `tests/test.sh` проверяет код возврата и ожидаемые строки вывода; запуск: `tests/test.sh <бинарник или скрипт>`; `tests/net_test.sh <папка сборки>` - наблюдатели, переподключение, остановка сервера |

ИИ при написании кода не использовался.
